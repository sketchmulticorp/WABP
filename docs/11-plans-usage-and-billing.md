# Plans, Usage, and Billing

## Separation of concerns

SaaS entitlements and customer charges must remain separate from Meta provider pricing and billing. Provider pricing and rules can change; do not hard-code them into plan logic.

## Plan model

A plan should support:

| Entitlement | Example key |
|---|---|
| Team users | `max_users` |
| WhatsApp numbers | `max_whatsapp_numbers` |
| Contacts | `max_contacts` |
| Monthly messages/usage | `monthly_message_limit` |
| Monthly campaigns | `monthly_campaign_limit` |
| Templates | `max_templates` |
| Storage | `storage_gb` |
| Automation | `automation_enabled` |
| Customer API | `api_enabled` |
| AI | `ai_enabled` |

Limits and feature flags must be evaluated server-side at creation and execution time. Hiding a UI control is not enforcement.

The database bootstrap creates only `MVP_INTERNAL`, a zero-price non-commercial plan with
environment-configurable development limits. It exists to make the first tenant usable
before commercial packages are approved; it does not establish launch pricing or billing
policy. An existing row with different limits causes the seed to fail rather than silently
changing active entitlements. See `BOOTSTRAP_SEED.md`.

## Subscription lifecycle

Support trial/active/past-due/suspended/cancelled/expired states as required by the selected commercial model. Store current period, renewal/expiry, selected plan, billing identity, and gateway references. Exact proration, grace period, renewal, refund, tax, currency, and invoice rules are open business decisions.

## Usage ledger

- Append usage events independently from dashboard counters.
- Include tenant, event type, quantity, related message/campaign/storage object, provider reference where useful, event time, and billing period.
- Deduplicate usage generated by retried jobs or duplicate webhooks.
- Make monthly counters rebuildable from the ledger.
- Track provider cost and customer charge as separate concepts.
- Preserve enough detail for support and billing reconciliation without storing unnecessary content.

For the pre-commercial MVP, outbound message quota uses the active plan's integer
`monthly_message_limit` and UTC calendar-month boundaries. A unit is reserved when the
common messaging service atomically creates an eligible Message in `CREATED`; idempotent
replay does not reserve again. A later provider failure does not automatically refund the
reservation. The ledger remains the source for reconciliation, and approved commercial
billing periods may replace the UTC calendar-month rule before launch.

## Enforcement points

- User invitation/activation.
- WhatsApp account connection.
- Contact creation/import completion.
- Template/automation creation or publication.
- Campaign preflight and dispatch.
- Manual or automated outbound send.
- File/media upload.
- Customer API and AI access.

Define whether a limit blocks immediately, allows a grace amount, queues until renewal, or requires upgrade. The UI must display current usage, limit, period, and the action needed.

## Plan changes

Upgrades may apply immediately; downgrades must define what happens when current data exceeds the new plan. Prefer preserving data with restricted creation/execution rather than destructive deletion. All plan and subscription changes are audited.

## Billing integration

CLAR-083 approves one future entitlement workflow for both online and offline payments.
For offline/cash collection, Super Admin records append-only payment evidence first and
then performs a separate, explicitly confirmed and audited subscription command that
selects the plan, effective period and status. Recording money alone continues to grant
no entitlement. A future gateway must feed the same workflow through an idempotent
adapter/webhook rather than create a second subscription model; gateway implementation
remains deferred.

Subscription expiry or billing suspension should preserve tenant data and approved
read-only access while server-side policy blocks new campaigns, outbound messages,
imports and other quota-consuming creation or execution. This billing state is distinct
from tenant suspension for security, abuse or policy, which may revoke workspace access.
Super Admin owns tenant-level billing/subscription controls; ordinary Tenant User account
management remains with the Tenant Admin. TASK-093 owns the detailed capability/state
contract and implementation. Pricing, currencies, partial-payment allocation, grace,
renewal-date calculation, proration, taxes, invoices and refunds remain open decisions.

Until the payment gateway work is approved, Super Admin may create append-only manual
payment records with tenant, amount in minor currency units, ISO currency, paid time,
reference, and optional operational note. References are unique per tenant and all writes
are audited. This ledger is not a gateway adapter, invoice system, or payment processor.

CLAR-040 includes manual payment visibility/recording in the MVP through TASK-080. Tenant
history omits platform-only operational notes. Payment recording never activates/extends
subscriptions. Display quota reservations separately from message statuses and money; do
not compute a balance due, Meta charges or cross-currency totals. See ESSENTIAL_REPORTING.md.

Payment gateway, supported commercial countries/currencies, taxes, invoicing, refunds and
reseller handling remain open/deferred. Keep a future billing provider behind an adapter
and process gateway webhooks idempotently; no such integration is added here.
